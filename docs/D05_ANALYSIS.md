# Анализ выгрузки D05

Источник требований: `Проект_D05_D06_ред_0.4.docx`, редакция от 12.11.2026. Документ помечен как рабочий проект для согласования, не утверждён.

## Что должна делать выгрузка

1. Принимать выбранный GF-файл и отбирать записи с `DN_LIST_RESULT_CODE = 207`.
2. Группировать записи по МО из `ATTACH_MCODE`. Записи без прикрепления не включать.
3. Формировать отдельный XML-пакет для каждой МО по каждому GF. Пакеты объединять в ZIP.
4. Не допускать повторов ключа `ENP + GROUP_RH_CD` внутри одного пакета.
5. Создавать постоянный `TASK_ID`. При повторном 207 для того же ключа в следующем GF увеличивать `REPEAT_CNT` и указывать `PREV_TASK_ID`.
6. Исключать умерших и незастрахованных на дату формирования.
7. Формировать XML в Windows-1251 по XSD из приложения Б. ZIP и XML должны иметь имена вида `D05M<CODEM>T34_YYMMNNN`; период брать из GF, срок ответа по умолчанию — 16-е число месяца формирования.

## Состав данных D05

- Заголовок: версия, коды МО `CODE_MO` и `CODEM`, дата, имя пакета и исходного GF, год/месяц, номер пакета, крайний срок и число задач.
- Задача: `ZAP`, `TASK_ID`, код результата 207, счётчик повторов и необязательный `PREV_TASK_ID`.
- Застрахованное лицо: ЕНП, идентификатор GF, необязательный IDPAC, обязательные фамилия, имя, дата рождения и пол; отчество необязательно.
- ДН: код и наименование группы, диагноз МКБ-10, необязательные профиль и специальность врача.
- TRIGGER необязателен и переносит сведения о медицинском случае из GF.

## Что найдено в текущей базе

В `TF_SISZL` есть `gf_person`, `gf_dn_list_result`, `gf_dn_plan_result`, `gf_trigger` и журналы импорта/экспорта. В `gf_person` есть ЕНП, дата рождения, пол, `ATTACH_MCODE`, поля группы ДН и `DN_PRVS`; триггерные данные хранятся отдельно в `gf_trigger`.

В базе не найдены таблицы или представления с:

- ФИО и сведениями о смерти/действующем страховании из регионального сегмента ЕРЗ;
- соответствием `ATTACH_MCODE → CODEM/CODE_MO` (T001/F003);
- справочником `group_rh` для короткого наименования группы и резервного кода специальности;
- IDPAC из ранее принятых D01;
- историей D05-задач для стабильного `TASK_ID`, `REPEAT_CNT` и `PREV_TASK_ID`.

Для тестового режима источник ФИО заменён синтетической генерацией, а оба кода МО копируются из `ATTACH_MCODE`. Смерть/страхование не фильтруются, `IDPAC=0`, `GROUP_RH_NAME=group_rh={код}`, `TASK_ID` нумеруется с 1, `REPEAT_CNT=1`, `PREV_TASK_ID` пропускается. Эти правила позволяют собрать тестовый пакет, но не являются рабочей продукционной выгрузкой.

## Предлагаемая интеграция

Тестовая операция доступна по `GET /api/v1/dn/files/{fileId}/export/d05-test`; необязательный `moCode` ограничивает выгрузку одной МО. Ответ — внешний ZIP с отдельным ZIP на каждую МО и XML Windows-1251 внутри. UI содержит действие «Тестовая выгрузка D05» на экране выбранного GF; введённый фильтр МО применяется к тестовой выгрузке. Перед продукционной реализацией подключить источники из списка выше, заменить синтетические значения и завести постоянную историю задач.

Для проверки использован `gf-11` (`GF34_2607.xml`) и `ATTACH_MCODE=010013`: сформирован пакет с 9 задачами. В `gf-23` (`GF34_2608.xml`) записей с кодом 207 нет. Для GF34_2607 найдено около 1,4 млн исходных строк 207 по 521 МО, поэтому для ручной проверки задавайте конкретный код МО.

Требования D06 и остаточные вопросы проекта (раздел 14.2) не должны блокировать формирование D05, но редакцию 0.4 следует считать согласуемым проектом, а не утверждённым форматом.

## Исходный замер текущего `d05-test` (T1)

Дата: 19.11.2026. Целевая выборка: `gf-11` (`GF34_2607.xml`), полный файл без `moCode`; ориентир объёма из предыдущего анализа — около 1,4 млн строк с кодом 207 по 521 МО. Запросы выполнялись последовательно к локальному API (`http://localhost:5080`) с отдельным `progressId` на каждый проход. Клиент фиксировал время от отправки запроса до получения HTTP-заголовков и до завершения чтения тела ответа.

| Проход | HTTP | До заголовков, с | Полное время, с | Результат |
|---|---:|---:|---:|---|
| 1 | 500 | 35,022 | 35,028 | Ошибка до начала ZIP-ответа |
| 2 | 500 | 7,353 | 7,353 | Ошибка до начала ZIP-ответа |
| 3 | 500 | 0,002 | 0,002 | Ошибка до начала ZIP-ответа |

Это не успешные значения TTFB: ни в одном проходе тело ZIP не было сформировано. По журналу API первый запрос завершился `SqlException` (`Execution Timeout Expired`, error -2) в предварительном `existsSql` (строка 408 `SiszlApi.cs`), до выполнения основного запроса выгрузки. При следующих попытках SQL Server перестал принимать соединения в пределах короткого `ConnectTimeout`; это видно в журнале API. Следовательно, три числа выше — только наблюдаемая задержка до неуспешного ответа, их нельзя сравнивать как производительность экспорта.

`SET STATISTICS TIME, IO` и фактический план для основного запроса не получены: endpoint завершился на предварительной проверке, а текущая реализация не экспортирует сообщения статистики SQL-клиенту. Для пригодной исходной точки повторить три прохода после восстановления доступности SQL Server и включить сбор плана/статистик на сервере (либо выполнить запрос из приложения в диагностическом режиме). Пока T1 остаётся незавершённым; приведённые ошибки сохранены для воспроизводимости.

## Индексы GF для T3

19.11.2026 в `TF_SISZL` применены миграции `migrate/001_AddGfQueryIndexes.sql` и `migrate/002_AddGfResult207Index.sql` (sqlcmd с `QUOTED_IDENTIFIER ON`). Проверка `sys.indexes` подтвердила три индекса `001` и фильтрованный `IX_gf_dn_list_result_207_person_id` с предикатом `DN_LIST_RESULT_CODE='207'`.

На запросе отбора для `gf-11` фактический план показывает `Index Scan` по `IX_gf_dn_list_result_207_person_id` (1 396 800 строк кода 207) и `Index Seek` по `IX_gf_person_import_id_ATTACH_MCODE_ENP_id`; сканирования всей таблицы `gf_dn_list_result` нет. SQL Server без указания индекса предпочитал существующий широкий `IX_gf_dn_list_result`, поэтому D05-запросы явно указывают новый фильтрованный индекс. Фактический план сохранён в [D05_T3_actual_plan.sqlplan](D05_T3_actual_plan.sqlplan). Запрос вернул 1 396 800 строк.

## Однопроходный отбор `#d05` (T4)

19.11.2026 сравнил старую и новую сборки одного эндпоинта `d05-test` на полном `gf-11` без фильтра МО. Старый вариант был запущен до пересборки контейнера; новый — после. Оба запроса выполнены последовательно через API на `localhost:5080`, ZIP дочитан полностью.

| Метрика | Старая версия | Новая версия с `#d05` |
|---|---:|---:|
| HTTP / ZIP | 200 | 200 |
| До первых заголовков ответа, с | 6,586 | 8,851 |
| Полное время, с | 34,529 | 37,019 |
| МО-пакетов | 52 | 52 |
| Задач | 1 390 868 | 1 390 868 |
| Пропусков | 0 | 0 |

Сравнение распакованных ZIP показало одинаковое число задач для каждой из 52 МО (расхождений 0). На исходном отборе SQL также подтверждены 1 396 800 кандидатных строк, 5 932 дубля и 1 390 868 выбранных строк; значения совпали со счётчиками новой версии. Старая версия не печатала число дублей в README, но её выбранные строки и пакеты совпадают с числом `candidate_rows - duplicate_rows`. Проверки качества теперь выполняются SQL при заполнении `#d05`; C# получает уже прошедшие строки и сводку причин пропуска.

Заполнение `#d05` выполняется отдельной параметризованной командой после безпараметрического `CREATE TABLE`; `id` приводится к `bigint`, `@MoCode` имеет тип `varchar(20)`. Кластерный индекс создан по `(Skip, MoCode, Enp, GroupRhCode, Id)`, чтение выполняется в том же порядке. Сборка и оба сквозных запроса успешны.

Дополнительно проверен отбор одной МО (`moCode=340033`): новый маршрут вернул HTTP 200.

Успешной цифры T1 для TTFB нет: все три исходных попытки завершились HTTP 500 до ZIP-ответа. Поэтому T4 показывает прямое сравнение старой/новой реализаций (6,586 против 8,851 с до первых заголовков), но сопоставить его с успешным baseline T1 невозможно. Полное время новой версии на этом запуске также оказалось на 2,490 с больше старого.
