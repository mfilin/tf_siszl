# REST API: учёт файлов ДН

Документ описывает API для трёх экранов прототипа: журнала GST/GPT/GF, записей файла GF и сводки результатов сверки. Все URL ниже относительные к базовому `/api/v1`. JSON кодируется в UTF-8. Часовой пояс для отображения дат задаёт клиент; даты бизнес-событий передаются как ISO 8601.

## Модель данных и правила

GF содержит два независимых результата сверки: `DN_LIST` для записи из GST и `DN_PLAN` для записи из GPT. Их коды, даты, файлы-источники и описания нельзя сводить в одно поле. В таблице и карточке записи показываются обе части раздельно.

Поле записи GF строится по таблице 4 межсистемного описания (P5.00): ENP, DN_PATIENT_ID, GROUP_RH_DS, GROUP_RH_CD, DN_LIST и DN_PLAN. В DN_LIST важны DN_LIST_FILENAME, CODE_L, DN_LIST_RESULT_CODE, DN_LIST_DATE_CHEKING и DN_LIST_RESULT_DESCR; в DN_PLAN — DN_PLAN_FILENAME, CODE_P, DN_PLAN_RESULT_CODE, DN_PLAN_DATE_CHEKING и DN_PLAN_RESULT_DESCR. Пол и дата рождения, СМО, прикрепление, сведения DN_GIS и другие поля схемы могут возвращаться в `patient` / `gisEvidence` и показаны в карточке при наличии.

`DN_PATIENT_ID`, пол, даты рождения и прикрепления в GF опциональны по схеме; отсутствие значения передавать как `null`, а не придумывать. Поля `CODE_L` и `CODE_P` относятся к собственным строкам GST/GPT и могут отсутствовать, если соответствующая ветвь результата отсутствует. Для классификации результатов и текста рекомендации клиент использует актуальный справочник API; UI не должен повторно кодировать правила сверки.

## 1. Журнал файлов

### `GET /api/v1/dn/files`

Постраничный журнал файлов региона текущего пользователя.

Параметры запроса:

| Параметр | Тип | Описание |
| --- | --- | --- |
| `q` | string | Поиск по имени файла (подстрока) |
| `type` | `GST`, `GPT` или `GF` | Тип файла |
| `periodFrom`, `periodTo` | `YYYY-MM` | Диапазон отчётных периодов включительно |
| `status` | string | Нормализованный статус обработки |
| `direction` | `inbound\|outbound` | Входящий или исходящий |
| `page` | integer, default `1` | Номер страницы, начиная с 1 |
| `pageSize` | integer, default `25`, max `100` | Размер страницы |
| `sort` | string | `createdAt:desc` по умолчанию; поддержать `period`, `type`, `status`, `recordCount`, `createdAt` |

Ответ `200`:

```json
{
  "items": [
    {
      "id": "file_01J...",
      "type": "GF",
      "fileName": "GF34_2609.xml",
      "period": "2026-09",
      "direction": "inbound",
      "recordCount": 20490,
      "status": "processed",
      "createdAt": "2026-10-20T11:03:00Z",
      "fileSizeBytes": 11744051,
      "sourceFileName": null,
      "error": null
    }
  ],
  "page": 1,
  "pageSize": 25,
  "totalItems": 9,
  "totalPages": 1
}
```

Статусы API: `queued`, `processing`, `processed`, `sent`, `failed`. Клиент отображает локализованные подписи и не выводит техническую ошибку без `error`. `recordCount` — количество записей самого файла; для ещё не обработанного файла значение может быть `null`.

### `GET /api/v1/dn/files/summary`

Агрегаты для карточек над журналом. Поддерживает те же фильтры `periodFrom`, `periodTo`, `type` и `status`, что и список.

```json
{
  "totalFiles": 9,
  "outboundGstGpt": 6,
  "inboundGf": 3,
  "failedFiles": 1,
  "asOf": "2026-10-20T11:03:00Z"
}
```

### `GET /api/v1/dn/files/{fileId}`

Полная карточка файла. Возвращает поля списка, а также `checksum`, `processingStartedAt`, `processingFinishedAt` и структурированную ошибку `error: { code, message }` либо `null`. Для неизвестного/недоступного региону файла — `404`.

## 2. Записи файла GF

### `GET /api/v1/dn/files/{fileId}/records`

Возвращает строки GF для таблицы и поиска. Допустим только файл типа `GF`; для другого типа вернуть `409` с кодом `FILE_TYPE_NOT_SUPPORTED`.

Параметры:

| Параметр | Тип | Описание |
| --- | --- | --- |
| `q` | string | Поиск по ENP, DN_PATIENT_ID, CODE_L, CODE_P |
| `category` | string | Категория одного из результатов GST/GPT |
| `resultCode` | integer | Код результата в любой из ветвей DN_LIST/DN_PLAN |
| `moCode` | string | Код МО из сведений о прикреплении/наблюдении (когда доступен) |
| `page` | integer, default `1` | Номер страницы |
| `pageSize` | integer, default `25`, max `100` | Размер страницы |
| `sort` | string | `enp:asc`, `enp:desc`, `resultDate:desc` |

Пример ответа `200`:

```json
{
  "fileId": "file_01J...",
  "fileName": "GF34_2609.xml",
  "items": [
    {
      "enp": "3400000000000001",
      "dnPatientId": "DN123456",
      "diagnosisCode": "I10",
      "groupRhCode": 1,
      "patient": {
        "sexCode": 2,
        "birthDate": "1964-05-03",
        "smoCode": "34002",
        "attachMoCode": "340001",
        "attachDate": "2024-02-01",
        "smoRegionCode": "34"
      },
      "dnList": {
        "period": "2026-09",
        "fileName": "GST34_2609_N1.xml",
        "code": "L2609-01001",
        "resultCode": "201",
        "resultDate": "2026-10-20",
        "resultDescription": "Эпизод зарегистрирован"
      },
      "dnPlan": {
        "period": "2026-09",
        "fileName": "GPT34_2609_N1.xml",
        "code": "P2609-01001",
        "resultCode": 301,
        "resultDate": "2026-10-20",
        "resultDescription": "Принято к информированию"
      },
      "insertedAt": "2026-10-20T11:00:00Z",
      "updatedAt": "2026-10-20T11:03:00Z"
    }
  ],
  "page": 1,
  "pageSize": 25,
  "totalItems": 20490,
  "totalPages": 820
}
```

Коды результатов в схеме могут быть строковыми для DN_LIST и числовыми для DN_PLAN — API вправе нормализовать оба в строку при условии, что исходное значение не теряется. Приведённый ответ сохраняет исходный тип каждого поля. Код МО (`moCode`) берётся из атрибутов пациента/прикрепления, не из макетного поля `MCOD`: в самом GF нет единого поля `MCOD` для обеих ветвей.

### `GET /api/v1/dn/files/{fileId}/records/{recordKey}`

Подробная карточка сверки. `recordKey` — непрозрачный серверный идентификатор строки, возвращаемый списком (рекомендуется добавить `id` к каждому `item`). Отдаёт полный набор данных из DN_LIST, DN_PLAN и DN_GIS, включая триггерный случай медицинской помощи, если он присутствует. Доступ только в пределах региона/роли текущего пользователя.

### `GET /api/v1/dn/files/{fileId}/records/export`

Экспортирует строки после применения тех же `q`, `category`, `resultCode`, `moCode`, `sort`, что и таблица. Параметры пагинации игнорируются, экспорт включает весь отфильтрованный набор. Ответ: `200 text/csv; charset=utf-8`, UTF-8 BOM, разделитель `;`, заголовки `ENP;DN_PATIENT_ID;DIAG_CODE;CODE_L;DN_LIST_RESULT_CODE;CODE_P;DN_PLAN_RESULT_CODE`. Имя файла формируется из исходного GF, например `GF34_2609_filtered.csv`. Для больших выгрузок можно заменить синхронный ответ экспортной задачей `POST /exports` + `GET /exports/{id}`; клиент скачивает файл по готовности.

## 3. Сводка сверки по GF

### `GET /api/v1/dn/files/{fileId}/analytics`

Сводка по одному GF-файлу. Для каждого результата учитывается строка проверки: запись может учитываться отдельно в GST и GPT. Счётчики должны быть раздельны по ветви; не объединять одинаковые коды в разных классификаторах.

Параметры: `repeatPeriods` — минимальное число последовательных отчётных периодов для повторяющейся ошибки (default `2`, min `2`), `top` — размер списка частых кодов (default `6`, max `20`).

```json
{
  "fileId": "file_01J...",
  "fileName": "GF34_2609.xml",
  "recordCount": 20490,
  "checks": { "gst": 20490, "gpt": 20490 },
  "categories": [
    { "type": "GST", "category": "accepted", "count": 17300, "percent": 84.4 },
    { "type": "GPT", "category": "fix_and_resend", "count": 420, "percent": 2.1 }
  ],
  "topResultCodes": [
    { "type": "GPT", "code": "399", "description": "Ошибки форматно-логического контроля", "category": "fix_and_resend", "count": 117 }
  ],
  "repeatedErrors": [
    {
      "dnPatientId": "DN123456",
      "moCode": "340001",
      "type": "GST",
      "code": "204",
      "periodCount": 2,
      "periods": ["2026-08", "2026-09"],
      "recommendation": "Уточнить статус полиса в ФЕРЗЛ, затем передать запись повторно."
    }
  ],
  "generatedAt": "2026-10-21T11:00:00Z"
}
```

`categories` и `topResultCodes` допускают нулевые значения/пустой массив. `percent` считается от общего числа проверок именно этой ветви (`checks.gst` или `checks.gpt`). Повторяющаяся ошибка — один и тот же `DN_PATIENT_ID` + тип ветви + код результата как минимум в N последовательных отчётных периодах, не просто несколько повторов строки в одном GF. Для закрытых/не требующих действия результатов рекомендация может быть `null`.

## Общие справочники и ошибки

### `GET /api/v1/dn/dictionaries/result-codes`

Возвращает справочники результатов отдельно для `GST` (DN_LIST) и `GPT` (DN_PLAN): код, исходное описание, категория UI, действие/рекомендация. Справочники кодов DN_PLAN 301–399 описаны в межсистемном документе; коды DN_LIST и практические правила должны браться из Приложения 1 и согласованной владельцами данных актуальной версии, а не генерироваться интерфейсом.

Стабильные категории API и подписи интерфейса: `accepted` — «Принято», `accepted_with_warning` — «Принято с замечанием», `fix_and_resend` — «Исправить и отправить», `verify_basis` — «Проверить обоснованность», `closed_exclude` — «Закрыт / исключить», `follows_gst` — «Следует за GST», `missing_gst` — «Нет в списках GST». Параметр `category` использует стабильное значение API, а не локализованную подпись.

### `GET /api/v1/dn/dictionaries/diagnoses`

Список допустимых диагнозов/профилей для фильтров и подсказок. Источник приложенных материалов — лист «Диагнозы шаблонов для правил» книги `Приложение_3_полный_список_диагнозов_для_БСК_ЗНО_Эндо.xlsx` (1272 значения кодов МКБ-10). В ответе добавить версию справочника и дату действия.

Ошибки возвращаются в едином формате:

```json
{
  "error": {
    "code": "FILE_NOT_PROCESSED",
    "message": "Результат сверки ещё не готов",
    "details": null,
    "requestId": "req_01J..."
  }
}
```

HTTP статусы: `400` неверный фильтр/пагинация, `401` нет сессии, `403` нет доступа к региону, `404` файл или строка не найдены, `409` операция неприменима (например, строки запрошены у GST), `422` файл не обработан, `500` внутренняя ошибка. Для `processing`-файла список строк/аналитика отвечает `409` или `422` с `FILE_NOT_PROCESSED`; UI показывает состояние обработки и повторяет запрос позже.

## Соответствие экранов

| Экран | Вызовы |
| --- | --- |
| Журнал файлов | `GET /files`, `GET /files/summary`, `GET /files/{fileId}` |
| Строки GF и карточка строки | `GET /files/{fileId}/records`, `GET /records/{recordKey}`, `GET /records/export`, справочник результатов |
| Сводка по периоду | `GET /files/{fileId}/analytics`, справочник результатов |

## Открытые решения для команды

1. Приложенный макет показывает общий список GST/GPT/GF и строки GF. В материалах сущность GF содержит ветви `DN_LIST` и `DN_PLAN`; экран поэтому должен фильтровать и экспортировать обе ветви. Вывод макета «ENP / DN_PATIENT_ID / CODE_L / CODE_P / МО / диагноз» — компактное представление, не буквальная структура XML.
2. В примере GF поле `DN_PLAN_PERIOD` в документе описано как дата, хотя заголовок поля указывает период; сериализовать его следует по фактической XSD/обменным файлам и зафиксировать формат с владельцем интеграции.
3. В исходном HTML описания `201–299`/`301–399` и рекомендации встроены в демонстрационный код. Перед включением клинически значимых подсказок согласовать их с владельцем актуального Приложения 1 и не считать макет источником нормативного справочника.
